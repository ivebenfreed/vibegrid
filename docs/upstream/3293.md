## VibeGrid today = 83.7k LOC in three layers

| Layer | What | ~LOC | On a re-factor |
|---|---|---|---|
| **DATA** | row store, windowing, mutations, substrate coupling | ~9k | Mostly **dies/thins with #3283**; remainder → a DataSource seam |
| **ENGINE** | virtualization, slot pooling, input/gesture, selection, fill, coordinate math, sort/filter eval | ~30–35k | The decision axis: keep / re-base on GridCore / rewrite |
| **SKIN** | slot renderers, affordances, editor UIs, view modes, filter/view UI, prop API, DOM/ARIA contract | ~40k | **Keep on every path** — this is VibeGrid's identity |

The key structural gap vs gp-grid: **VibeGrid has no instruction boundary.** gp-grid's `GridCore` emits a `GridInstruction` stream (~24 kinds: slot create/assign/move/destroy, setContentSize, updateHeader, setSelectionRange, startEdit, fill…) that a dumb renderer applies. VibeGrid instead couples stores → renderer directly via MobX reactions + version counters (`dataVersion`/`configVersion`/`structureVersion` in TableCoreStore), and the renderer reaches back into stores. **Introducing that instruction seam is the #1 lesson to steal — with or without gp-grid's code.**

## Recommendation (unchanged after mapping, now grounded)

**Split the idea by economics — the two halves point opposite ways:**

1. **Decompose the DATA + state layer with gp-grid as teacher — worth it on any path.** Introduce the instruction boundary and split the god-stores (TableCoreStore 2745, InteractionStore 1659, EditingStore 1297) along gp-grid's RowData/Selection/Edit manager seams. Low-risk, incremental, shippable store-by-store, zero consumer churn, and **most of TableCoreStore's bulk is substrate/sparse code that #3283 removes anyway** — so this is partly free.

2. **Do NOT rewrite the ~30k ENGINE for elegance.** That's SlotPool + ScrollVirtualization + Input/Gesture + Selection/Fill mechanics. gp-grid already solved 500k scroll-compression, worker parallel-sort, slot recycling. Re-solving them cleaner = max effort, zero leverage. Either **keep** them (they work at 200k rows for DEB today) or, if the *engine itself* is the maintenance pain, that's the exact case where **re-basing on GridCore's code beats rewriting your own**.

**So: gp-grid as teacher for the seams/decomposition; gp-grid as code only where re-solving is waste; freeze what works.**

## The one gating decision + sequencing

**Gate:** Does VibeGrid's *engine* (virtualization/input/selection/fill) actually generate maintenance pain, or is the pain the DATA layer (substrate)? The sweep evidence says the recent bug stream (#3105/#3111/#3112/wedges) was **substrate/data coupling, not engine** — which argues the engine is fine and #3283 + a state-layer decomposition gets ~80% of the "slim, decoupled" win without touching the engine at all.

**Sequence:**
1. Land #3283 P1 (already next on the epic). Re-measure — the engine-vs-data split becomes concrete.
2. Decompose the state layer (instruction boundary + god-store split) — the do-regardless win.
3. **Then** decide engine keep-vs-re-base from real post-#3283 pain, not today's coupled baseline.
